# Releasing

This repository uses [release-please](https://github.com/googleapis/release-please) to version `@module-federation/nuxt` and write its changelog from Conventional Commits. Publishing to npm happens in a separate workflow through GitHub Actions trusted publishing.

## How it fits together

| Piece                                  | Role                                                                                                                               |
| -------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| `.github/workflows/pr.yml`             | Requires every PR title to be a Conventional Commit. PRs are squash-merged, so the title becomes the commit release-please reads.  |
| `.github/workflows/release-please.yml` | Runs on every push to `main`. Opens or updates the release PR, and creates the GitHub release and tag once that PR is merged.      |
| `.github/workflows/release.yml`        | Dispatched by `Release Please` for each new release. Re-runs the release gate and publishes to npm with provenance.                |
| `release-please-config.json`           | release-please settings: package path, tag format, pre-1.0 bump rules, changelog sections.                                         |
| `.release-please-manifest.json`        | The last released version. release-please updates it in each release PR; do not edit it by hand except to bootstrap or repair.     |
| `packages/nuxt/CHANGELOG.md`           | Generated by release-please. Excluded from Prettier in `.prettierignore` because the generated Markdown is not Prettier-formatted. |

Only commits that touch `packages/nuxt` count toward a release. Changes limited to `apps/`, `e2e/`, `test/`, or CI do not open a release PR on their own.

## Writing releasable commits

Use a Conventional Commit PR title. The type decides the version bump and changelog section:

| PR title                                                 | Changelog section | Bump while `< 1.0.0` | Bump from `1.0.0` |
| -------------------------------------------------------- | ----------------- | -------------------- | ----------------- |
| `fix: …` / `fix(nuxt): …`                                | Bug Fixes         | patch                | patch             |
| `perf: …`                                                | Performance       | patch                | patch             |
| `feat: …`                                                | Features          | minor                | minor             |
| `feat!: …` or a `BREAKING CHANGE:` footer                | ⚠ Breaking        | minor                | major             |
| `docs:`, `chore:`, `refactor:`, `test:`, `build:`, `ci:` | hidden            | none                 | none              |

While the package is pre-1.0, `bump-minor-pre-major` keeps breaking changes on minor releases instead of jumping to `1.0.0`. Features and breaking changes both bump minor until then, so call out breaking changes clearly in the PR title.

Write the title in release-note language: it is copied verbatim into `CHANGELOG.md` and the GitHub release.

To fix a changelog entry after merge, edit the merged PR's body to add an override block, then re-run `Release Please`:

```
BEGIN_COMMIT_OVERRIDE
fix(nuxt): corrected release note text
END_COMMIT_OVERRIDE
```

To force a specific version, set `"release-as": "0.3.0"` under `packages/nuxt` in `release-please-config.json`, merge it, and remove it in a follow-up once that release ships. A `Release-As:` commit footer only works on a commit that touches `packages/nuxt`; commits outside the package path are ignored.

## Release gate

The `Release` workflow repeats these checks before publishing. Run them locally before merging larger changes:

```bash
pnpm install --frozen-lockfile
pnpm typecheck
pnpm build
pnpm test
pnpm pack:nuxt
pnpm format:check
```

Also exercise the production examples with `pnpm preview`. Confirm server-rendered remote markup, browser hydration, remote interactions, manifest loading, both remote entries, and all referenced `/_nuxt` assets.

## Stable release flow

1. Merge PRs with Conventional Commit titles into `main`.
2. `Release Please` opens or updates a release PR (titled like `chore(main): release 0.2.0`). It bumps `packages/nuxt/package.json` and `.release-please-manifest.json`, and adds the new section to `packages/nuxt/CHANGELOG.md`. Each new releasable commit on `main` updates the same PR, and `Release Please` dispatches `CI` and `E2E Tests` on the release branch. Their results show on the PR's head commit.
3. Review the release PR: version, changelog wording, and the packed file list from CI (`pnpm pack:nuxt`).
4. Merge the release PR after CI passes.
5. `Release Please` runs again on the merge commit, creates the tag `<version>` (for example `0.2.0`, no `v` prefix), and publishes a GitHub release with the changelog section as its notes.
6. `Release Please` dispatches `Release` with `version=latest`, `branch=main`, and `tag=<version>`. It checks out the tag, verifies it matches `packages/nuxt/package.json`, re-runs the release gate, and publishes to npm with dist-tag `latest`.
7. Verify the npm version, provenance, README, exports, and `latest` dist-tag.

If the npm publish fails after the GitHub release exists, fix the cause and re-run the failed `Release` run, or run `Release` manually with `version=latest`, `branch=main`, and `tag=<version>`. Publishing is skipped when the exact version is already on npm with the requested dist-tag.

## Required setup

- **"Allow GitHub Actions to create and approve pull requests"** enabled under Settings → Actions → General. `Release Please` runs with `GITHUB_TOKEN` and cannot open the release PR without it.
- No release token is needed. GitHub does not start workflows from push, pull request, or release events created with `GITHUB_TOKEN`, so `Release Please` dispatches `CI`, `E2E Tests`, and `Release` itself through `workflow_dispatch`, the one event that token can trigger. A GitHub release published by hand still triggers `Release` directly.
- **Squash merging** with the PR title as the commit message, so the validated title is what lands on `main`.
- **GitHub `Publish` environment** used by `release.yml`.
- **npm trusted publisher** configured for:
  - repository: `module-federation/nuxt`
  - workflow: `release.yml`
  - environment: `Publish`

## Preview release

Run the `Release` workflow manually with:

- `version=next`
- `branch=main`

The workflow sets the version to the next patch plus `-next.<workflow-run-id>` (for example `0.1.1-next.123456789` when `main` is at `0.1.0`) and publishes it under the npm `next` dist-tag. The version change is not committed.

Every push and PR also gets a [pkg.pr.new](https://pkg.pr.new) build from `pkg-pr-new.yml` for install-by-URL testing without touching npm.

GitHub prereleases are not supported: release-please owns the `<version>` tags, and `Release` rejects a published prerelease.

## Publish safeguards

- The workflow publishes from `packages/nuxt` with npm provenance.
- The workflow publishes only commits reachable from `main` and reruns the full release gate before publishing.
- Release tags must match `packages/nuxt/package.json` exactly and must not start with `v`.
- Stable releases use `latest`; previews use `next`.
- Publishing skips only when the exact npm version already exists and the requested dist-tag already points to it.
- Publishing fails when an existing version would require dist-tag promotion. Create a new semver version instead.

## Changing the automation

- Bootstrapping: `.release-please-manifest.json` started at `0.1.0`, matching the existing `0.1.0` tag and GitHub release. release-please collects commits after that tag.
- Tag format is controlled by `include-component-in-tag: false` and `include-v-in-tag: false`. Changing either breaks the tag check in `release.yml` and release-please's lookup of previous releases.
- If release-please loses track of the previous release (for example after a tag rename), set top-level `last-release-sha` in `release-please-config.json` for one run, then remove it.
